# The discriminant-image obligation: what a `discriminant_image()` migration preserves, and what it hides

Written after an outside controller edited `tests/acceptance/test_boundaries.sage` in this project, replacing the
two typed constructions with `group.discriminant_image()`, adding supergroup identity checks, and then weakening
those to cardinality equality. The worktree has since been restored; this note records what the **original**
obligation is, so a future migration can be judged against it rather than against a number.

## The original form, exactly as it stands at `0a4a05bd`

`tests/acceptance/test_boundaries.sage:224-230` (the 87 Enriques cases):

```python
target = anti_invariant.discriminant_group().orthogonal_group()

image = target.subgroup_on(tuple(g.discriminant_morphism() for g in group.group_generators()))

assert int(image.cardinality()) == case["group_order"]
assert _counts(group) == (case["line_orbits"], case["plane_orbits"], case["flag_orbits"])
```

and `:243-248` (the three classical-index cases):

```python
target = anti_invariant.discriminant_group().orthogonal_group()

image = target.subgroup_on(tuple(g.discriminant_morphism() for g in group.group_generators()))

assert int(image.cardinality()) == case["gamma_h_over_stable_order"]
assert _ORDER_O_PLUS_10_2 // int(image.cardinality()) == case["index_in_O_plus_N"]
```

Nothing else in either test touches the image.

## Three obligations are carried by that expression, not one

1. **Generator realization.** For every generator `g` of `Γ_h` the discriminant morphism `g.discriminant_morphism()`
   must be *constructible* as a typed object. This is the operation the Enriques and Dawes families are actually
   blocked on — producing the image of each generator, not the order of a group.
2. **Typed endpoint identity.** `image` is a subgroup **of that same `target`** (`N.discriminant_group()
   .orthogonal_group()`), because `subgroup_on` is a method of `target` and rejects elements of another parent. The
   assertion is meaningful because the image is *inside* `O(q_N)`, and that fact lives in the type, not in a number.
3. **Cardinality, and in the second test an index.** `image.cardinality()` must equal the published order, and the
   classical-index test divides the recorded `|O^+(N)|` by it.

## Would an exact image API preserve the obligation?

**It preserves it if and only if the new API's contract fixes all three of the above**, concretely:

* it returns a subgroup of the **same** `target` parent, with an inclusion into `target` (so endpoint identity is a
  property of the object, not of a comment);
* it is **defined** as the subgroup generated by the discriminant morphisms of the given generators — either by
  documenting that equality, or by exposing the generator images so the test can build
  `target.subgroup_on(images)` itself and assert equality of subgroups;
* `cardinality()` on the result is that subgroup's order.

**It conceals the generator-realization requirement if** it returns only an order, or returns a subgroup defined by
some other route whose agreement with the generated subgroup is not part of the contract. In that case the two
assertions above still pass while obligation 1 has silently left the suite: nothing would then require that the port
can realize `g.discriminant_morphism()` for an actual generator, which is precisely the capability under test.

## Why cardinality equality cannot stand in for typed endpoint identity

Equal order does not identify a subgroup, and it does not place it inside anything. `S_3` has three distinct
subgroups of order 2; a group of order `p^2` has `p+1` of them. So
`image.cardinality() == case["group_order"]` is compatible with a *different* subgroup of the same order, and with a
subgroup of an object that is not `target` at all if the API ever returned one. The controller's intermediate
"supergroup identity" assertion (`image.supergroup() is target`) fixes only the ambient parent: it says which group
the subgroup lives in, not which subgroup of it, so even *that* check plus cardinality is strictly weaker than the
original expression, which names both the parent (by construction) and the generators (by construction).

The port-side rule that follows: keep the original expression, or replace it with something that asserts **subgroup
equality** against the generators' images. A cardinality comparison is never a substitute.
